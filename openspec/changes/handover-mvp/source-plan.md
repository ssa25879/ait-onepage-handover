# 인계한장 — 앱인토스 미니앱 개발 기획서

> **버전:** v1.1\
> **작성·수정 기준일:** 2026-10-22\
> **플랫폼:** 앱인토스(Apps in Toss) / WebView 미니앱\
> **개발 형태:** 1인 개발·바이브코딩\
> **예상 MVP 개발 기간:** 3~4일(외부 심사 기간 제외)\
> **문서 상태:** MVP 구현 완료, Android 실기기 테스트 미진행\
> **실기기 검증 범위:** **Android만 가능. iOS 실기기는 미검증으로 기록**

## 1. 프로젝트 개요 및 개발 목표

### 1.1 프로젝트 소개

**인계한장**은 아르바이트생, 교대근무자, 소규모 사업장 근무자가 업무 인수인계를 **템플릿 선택 → 내용 입력 → 저장 → 복사**의 짧은 과정으로 마칠 수 있게 하는 모바일 미니앱이다. 메신저·메모장에 제각각 작성해 발생하는 누락, 형식 불일치, 과거 기록 조회 불편을 줄이는 데 집중한다.

### 1.2 핵심 가치와 MVP 목표

- **빠른 작성:** 업무 유형별 템플릿과 안내 문구 제공
- **일관된 전달:** 완료 업무·진행 중 업무·전달사항을 같은 순서로 정리
- **개인 기록 관리:** 작성한 기록을 기기 로컬 저장소에서 조회·수정·삭제
- **간편한 외부 전달:** 메신저에 붙여 넣을 수 있도록 텍스트 일괄 복사
- **낮은 진입장벽:** 자체 회원가입·백엔드·별도 클라우드 연동 없음

첫 인수인계 작성부터 저장·복사까지 **2분 이내**에 완료할 수 있는 흐름을 UX 목표로 삼는다. 이는 확정된 사용자 측정 결과가 아닌 프로젝트 자체 목표이며, Android 테스트에서 확인한다.

### 1.3 초기 범위에서 제외

별도 로그인, 서버 데이터베이스, 실시간 공동 편집, 기기 간 동기화, 클라우드 복원, 유료 결제, AI 서버 요약은 MVP에서 제외한다. 사진 촬영·OCR은 구현 가능성만 우선 검증하고 일정에 여유가 있을 경우 추가한다.

## 2. 타깃 사용자와 실제 사용 시나리오

| 사용자 | 업무 상황 | 필요한 인수인계 |
|---|---|---|
| 카페·음식점 아르바이트생 | 마감·교대 | 청소, 원재료 부족, 예약·고객 요청 |
| 편의점·소매점 근무자 | 근무 교대 | 상품 보충, 재고 부족, 검수·시설 특이사항 |
| 일반 교대근무자 | 다음 근무조 인계 | 완료 업무, 미완료 업무, 주의사항 |
| 소규모 사업장 근무자 | 일일 업무 보고 | 당일 진행상황, 후속 처리 대상 |

### 시나리오 A — 카페 마감

1. 앱 실행 후 **카페·음식점** 템플릿을 선택한다.
2. 청소 완료, 원두 재고 확인 필요, 다음 날 예약 등의 내용을 입력한다.
3. 저장 후 **내용 복사**를 누른다.
4. 외부 메신저에서 직접 붙여 넣어 동료에게 전달한다.

### 시나리오 B — 편의점 교대

과거 기록을 참고하고 **편의점·소매점** 템플릿으로 새 기록을 작성한다. 보충 완료 품목과 미완료 검수 내용을 입력하고 저장·복사한다.

### 시나리오 C — 일반 교대근무

**일반 교대근무** 템플릿을 골라 완료·진행 중 업무 및 전달사항을 작성한다. 이전 기록을 참고할 수 있지만, MVP에서는 기록 간 자동 연결이나 공동 작성은 제공하지 않는다.

**핵심 흐름:** 홈 → 템플릿 선택 → 작성 → 저장·복사 → 외부 앱에 붙여 넣기\
**기록 흐름:** 홈 → 기록 목록 → 상세 → 수정·복사 또는 삭제

## 3. MVP 기능 명세 및 우선순위

**우선순위 정의:** P0는 3일 차까지 완료해야 하는 필수 기능, P1은 품질·출시 보완 기능, P2는 검증 결과에 따른 선택 기능이다.

| ID | 기능 | 우선순위 | 범위 | 수용 기준 |
|---|---|---|---|---|
| F-01 | 템플릿 선택 | P0 | 기본 업무 유형 3종 | 선택한 유형의 작성 화면 표시 |
| F-02 | 인수인계 작성 | P0 | 날짜·완료·진행 중·전달사항 | 여러 줄 입력, 공백 유효성 검사 |
| F-03 | 기록 저장 | P0 | 신규 기록 생성 | 저장 성공 후 재실행해도 조회 가능 |
| F-04 | 기록 수정 | P0 | 기존 내용 편집 | ID 유지, 수정 결과 반영 |
| F-05 | 기록 삭제 | P0 | 확인 후 삭제 | 선택한 기록만 제거 |
| F-06 | 내용 복사 | P0 | 읽기 쉬운 텍스트 생성 | 실제 클립보드 내용 일치 |
| F-07 | 과거 기록 조회 | P0 | 날짜순 목록·상세 | 전체 저장 기록 탐색 가능 |
| F-08 | 처리 결과 안내 | P0 | 저장·복사 성공/실패 | 실패를 성공으로 표시하지 않음 |
| F-09 | 배너 광고 | P1 | 기록 목록 하단 조건부 배치 | 광고 실패 시 핵심 사용성 유지 |
| F-10 | 작성 이탈 방지 | P1 | 미저장 변경 확인 | 취소하면 작성값 보존 |
| F-11 | 카메라 촬영 | P2 | 문서·메모 촬영과 임시 미리보기 | Android SDK 동작 확인 |
| F-12 | OCR | P2 | 이미지의 글자 추출 | 한국어 인식·성능 확인 후 적용 |

### 3.1 기본 템플릿 3종

- **카페·음식점 (`cafe`):** 청소·마감·재고, 준비 중 작업, 예약·고객 요청
- **편의점·소매점 (`retail`):** 상품 진열·보충, 재고·검수, 시설·고객 특이사항
- **일반 교대근무 (`general`):** 완료 업무, 진행 중 업무, 다음 근무자 전달사항

세 템플릿은 **동일한 3개 본문 필드**를 공유한다. 템플릿은 필드명 변경이나 복잡한 별도 스키마가 아닌 안내 문구·예시만 다르게 제공한다.

### 3.2 입력·저장 규칙

1. 기본 날짜는 현재 날짜이며 사용자 변경을 허용한다.
2. 본문 3개 중 하나 이상에 공백이 아닌 문자가 있어야 저장 가능하다.
3. 여러 줄 입력을 허용한다. 길이 제한은 실제 SDK 저장 한도·사용성을 검증한 뒤 결정한다.
4. 저장 성공 전까지 입력값을 유지한다. 실패한 저장을 성공으로 안내하지 않는다.
5. 수정 시 고유 ID·최초 작성 시각은 유지하고 수정 시각을 갱신한다.
6. 저장하지 않은 변경사항이 있는 상태에서 이동할 때 이탈 여부를 확인한다.
7. 동일한 날짜에 여러 기록을 만들 수 있다.

### 3.3 복사 형식

```text
[인계한장 - 업무 인수인계]

날짜: 2026-10-22
업무 유형: 카페·음식점

■ 완료 업무
- 매장 청소 완료
- 커피머신 세척 완료

■ 진행 중 업무
- 원두 재고 확인 필요

■ 전달사항
- 내일 오전 단체 예약 확인
- 우유 재고 보충 필요
```

빈 항목은 복사 결과에서 생략한다. 현재 편집 중인 내용을 **저장하지 않고 복사할 수도 있지만**, 복사가 자동 저장을 의미하지 않는다는 점을 UI로 명확히 한다. 메신저 자동 전송은 제공하지 않는다.

### 3.4 조회·삭제 규칙

기록 목록은 업무 날짜 기준 최신순으로 표시하며, 같은 업무 날짜는 최신 수정 시각 기준으로 정렬한다. 삭제 버튼은 사용자 확인 후 실행하고, 빈 목록에는 새로운 기록 작성으로 연결되는 안내를 제공한다.

## 4. 화면 구성과 사용자 흐름

| 화면 | 주요 UI | 핵심 동작 | 광고 여부 |
|---|---|---|---|
| 홈 | 앱 소개, 새 작성, 최근 기록(최대 3건) | 템플릿 선택·기록 목록 이동 | 없음 |
| 템플릿 선택 | 업무 유형 카드 3종 | 템플릿 선택 | 없음 |
| 작성·수정 | 날짜, 본문 3개, 저장·복사 | 기록 입력과 편집 | 없음 |
| 기록 목록 | 날짜, 업무 유형, 내용 미리보기 | 과거 기록 상세 이동 | 조건 충족 시 배너 1개 |
| 기록 상세 | 인수인계 전체 내용 | 수정·복사·삭제 | 없음 |

### 4.1 화면별 동작

- **홈:** 첫 사용자는 곧바로 새 작성, 기존 사용자는 최근 기록 또는 기록 목록으로 이동한다.
- **템플릿 선택:** 카페·음식점 / 편의점·소매점 / 일반 교대근무 카드 중 하나 선택.
- **작성·수정:** 키보드가 열린 상태에서도 입력 영역과 주요 버튼이 가려지지 않도록 스크롤과 Safe Area를 적용한다.
- **기록 목록:** 검색·필터는 후속 버전으로 미루고 날짜순 목록에 집중한다.
- **상세:** 수정·복사·삭제를 명확하게 분리하고 삭제 전 확인창을 제공한다.

### 4.2 예외 흐름

| 상황 | 기대 동작 |
|---|---|
| 빈 내용 저장 | 검증 메시지, 저장 중단 |
| Storage 실패 | 내용 보존, 재시도 안내 |
| 클립보드 실패 | 오류 안내, 기존 기록 영향 없음 |
| 작성 중 뒤로가기 | 미저장 변경사항 확인 |
| 기록 0건 | 빈 상태 안내, 작성 버튼 |
| 광고 로딩 실패 | 광고 공간 정리, 목록 정상 표시 |
| 카메라 권한 거부 | 수동 작성 계속 사용 가능 |

## 5. 기술 스택과 프로젝트 구조

### 5.1 채택 예정 기술

## 6. 데이터 모델과 저장 방식

### 6.1 기록 데이터

| 필드 | 타입 | 설명 |
|---|---|---|
| `id` | `string` | 기록 고유 ID |
| `templateId` | `string` | `cafe` / `retail` / `general` |
| `workDate` | `string` | 업무 날짜, `YYYY-MM-DD` |
| `completed` | `string` | 완료 업무 |
| `inProgress` | `string` | 진행 중 업무 |
| `notes` | `string` | 전달사항 |
| `createdAt` | `string` | 최초 작성 시각, ISO 8601 |
| `updatedAt` | `string` | 수정 시각, ISO 8601 |

### 6.2 저장 포맷

기록은 `ingye-hanjang:records:v1` 키 아래 `schemaVersion`과 `records` 배열을 JSON으로 직렬화해 저장하는 안을 사용한다. 저장·읽기·삭제는 공식 SDK의 `Storage.setItem`, `Storage.getItem`, `Storage.removeItem`을 우선 사용한다. 저장 중 오류가 발생하면 입력을 유지하고, 잘못된 형식이나 손상된 데이터를 **빈 배열로 간주해 자동 덮어쓰지 않는다**.

초기 데이터 규모와 로컬 저장소 한도를 테스트하고, 사진 원본은 기본적으로 기록에 영구 저장하지 않는다. 대용량 이미지를 JSON/문자열 저장소에 누적하지 않는다.

### 6.3 데이터 보존 제한

- 토스 앱 삭제·앱 데이터 초기화 시 기록이 사라질 수 있다.
- 다른 기기로 바꿔도 자동 복원되지 않는다.
- 같은 사용자의 여러 기기 간 동기화가 되지 않는다.
- 초기 버전에는 서버 백업이 없다.
- 중요한 내용은 **복사 기능으로 별도 보관**할 수 있도록 안내한다.

### 6.4 개인정보·내부 업무 정보

필수 개인정보 입력 없이 사용하도록 설계한다. 고객 정보·비밀번호·민감한 사업장 데이터를 입력하지 않도록 안내한다. 저장한 인수인계 **본문을 앱 자체 서버나 광고 이벤트에 전송하지 않는다**. 광고 SDK 자체는 네트워크를 사용할 수 있으므로 '앱 전체의 데이터가 외부로 전송되지 않는다'는 식으로 오해를 일으키지 않는다. 삭제 기능과 클립보드 복사에 따른 외부 유출 가능성을 안내하고, 디버그 로그에 본문을 기록하지 않는다.

## 7. 앱인토스 SDK 연동 및 출시 고려사항

### 7.1 SDK 초기 설정

1. 앱인토스 WebView 프로젝트를 공식 가이드에 따라 초기화한다.
2. 신규 프로젝트는 SDK 3.x를 기준으로 하되 설치 가능한 실제 버전을 확인한다.
3. `apps-in-toss.config.ts`의 설정과 콘솔 앱 식별자를 일치시킨다.
4. 토스 내비게이션 바, Safe Area, 뒤로가기, 라이트 모드를 확인한다.
5. Android 토스 앱에서 SDK 기능을 직접 검증한다. **iOS는 미검증 상태로 남긴다.**

### 7.2 공식 API 사용 범위

| 기능 | API | 확인/검증 상태 |
|---|---|---|
| 문자열 저장·읽기·삭제 | `Storage` | 공식 제공 확인, 동작 검증 전 |
| 텍스트 복사 | `Clipboard.setText` | 공식 제공 확인, Android 테스트 전 |
| 배너 광고 | `TossAds.initialize`, `TossAds.attachBanner` | 공식 제공 확인, 그룹 설정·동작 검증 전 |
| 카메라 촬영 | `Device.openCamera` | 공식 제공 확인, 권한·Android 테스트 전 |
| OCR | 전용 공식 API 미확인 | 외부 서버 없는 로컬 OCR 후보 검증 필요 |

SDK별 `isSupported()` 등 지원 여부 점검 기능은 공식 문서에서 실제 호출 대상과 사용법을 확인하고 적용한다.

### 7.3 광고 배치 전략

**운영 전제:** 현재는 **배너 광고 그룹만 사용 가능**하다. 다른 광고 유형은 권한·정책 변경 시 후속 검토한다.

| 후보 위치 | 평가 | 이유 |
|---|---|---|
| 홈 상단 | 비권장 | 새 작성 진입 동선을 방해 |
| 홈 하단 | 보류 | 스크롤 가능한 화면 조건 충족 여부 불명확 |
| 템플릿 선택 | 비권장 | 짧은 선택 화면과 간섭 |
| 작성·수정 화면 | 비권장 | 입력·저장·복사·키보드와 간섭 |
| **과거 기록 목록 하단** | **우선 채택** | 기록 조회 흐름 뒤에 제한적으로 배치 가능 |
| 기록 상세 | 비권장 | 수정·복사·삭제와 근접 위험 |

**초기 광고 규칙**

1. 기록 목록이 **실제로 스크롤 가능한 경우에만** 배너 광고 1개를 노출한다. (비게임 출시 체크리스트의 배너 노출 조건)
2. 목록 하단의 광고 영역을 본문 및 기록 카드와 구분한다. 저장·복사·삭제 버튼 부근에는 노출하지 않는다.
3. 광고 그룹명은 예시로 `기록목록_배너`를 사용한다. 실제 그룹 ID는 콘솔에서 발급받는다.
4. 개발 시 공식 테스트 광고 ID `ait-ad-test-banner-id`를 사용하고 운영 단계에 운영 ID로 변경한다.
5. 배너 로드·초기화 실패 시 광고를 숨기고 핵심 기능은 정상 작동하게 한다.
6. 화면 이탈 시 SDK 문서에 맞춰 광고 인스턴스를 정리한다. 중복 부착·임의 광고 갱신을 피한다.
7. 공식 지원 버전(토스 앱 5.241.0 이상), 너비·높이 권장사항, 로딩 상태 등 세부 조건을 개발 시작 시 재확인한다.
8. 기록이 없거나 스크롤되지 않는 화면에는 광고를 배치하지 않는다.

광고 그룹 변경이 가능하도록 설정값은 UI 컴포넌트에서 분리한다. 광고를 핵심 작업의 선행 조건으로 만들지 않는다.

### 7.4 사업자·정산·심사

공식 안내에서 인앱 광고의 사업자·정산 정보 등록 유예 규정을 설명하지만, 수익·등록 조건과 적용 대상은 콘솔 및 최신 약관을 최종 확인한다. 기존 공식 안내 기준으로 워크스페이스 누적 예상 광고 수익 **5,000원 미만**에 유예가 가능하고 도달 후 **5영업일** 유예기간이 설명되어 있었다. 다만 다른 광고 소개 자료에는 사업자 등록을 선행 단계로 안내하기도 하므로 **현재 프로젝트에 적용되는 실제 조건은 미확인**으로 둔다. 세법상 의무는 별도 검토한다.

**출시 준비 체크**

- 비게임 출시 심사 및 광고 정책 준수
- 제공 기능과 등록 정보·설명 문구 일치
- 토스 내비게이션 바, 뒤로가기, 안전 영역 확인
- 권한 요청과 거부 시 대체 흐름 보장
- 개인정보 입력 안내 및 실제 정보 처리 범위 점검
- 로고·아이콘·앱 설명·광고 그룹·운영 정보 준비
- Android 토스 앱 테스트 빌드 검증
- iOS 동작 및 호환성 **미검증** 기록

앱인토스 심사 **승인/실제 공개는 별도 단계**이며 3~4일 개발 일정에 포함하지 않는다.

### 7.5 카메라·OCR 가능성 검토

**사진 촬영**은 `Device.openCamera`를 통한 이미지 획득, 권한 허용/거부, 촬영 취소, 미리보기, 기존 입력 상태 보존을 Android에서 검증한다. 사진을 임의로 서버에 업로드하지 않는다.

**OCR**은 현재 공식 SDK 전용 기능을 확인하지 못했으므로 브라우저/기기 내에서 동작하는 로컬 OCR 기술을 우선 조사한다. 선정 전 검증 사항은 한국어 인식률, 모델 파일·번들 크기, 메모리, 처리 시간, 오프라인 가능 여부, 앱인토스 WebView 호환성이다. 인식 결과는 사용자에게 미리 보여주고 **명시적인 확인 후** 선택한 입력란에 삽입한다.

촬영이나 OCR을 충분히 검증하지 못하면 F-11/F-12는 MVP에서 제외하고 수동 작성만 제공한다. 구현하지 않은 기능을 앱 소개·출시 설명에 포함하지 않는다.

### 9.4 검증 환경: Android만

**확정된 실기기 테스트 환경은 Android이다.** 다음 항목을 실제 Android 기기와 토스 앱에서 테스트한다.

- 앱인토스 SDK 초기화·실행·뒤로가기
- 저장/불러오기 및 앱 종료·재실행 후 데이터 유지
- 클립보드 복사와 다른 앱에 붙여 넣기
- 배너 노출·스크롤 조건·실패 시 동작
- 카메라 권한·촬영·취소(선택 기능 구현 시)
- 모바일 키보드가 열린 상태의 레이아웃, Safe Area 및 버튼 접근성
- 긴 텍스트, 여러 줄, 작은 화면에서의 스크롤·터치
- 불안정한 네트워크에서 광고 실패와 로컬 기능 분리

**iOS 제한:** iOS 실기기 테스트는 보유 기기가 없어 **진행하지 않는다**. iOS 전용 오류, 권한 차이, SDK 동작과 UI 호환성은 **미검증**으로 최종 보고서에 남긴다. Android 검증 결과를 iOS까지 일반화하지 않는다. 이후 iOS 기기 확보 시 별도 회귀 테스트를 수행한다.

**자동화/정적 검사:** 타입 검사·프로덕션 빌드, 순수 데이터 유효성 검사·텍스트 포맷팅과 저장 모듈의 적절한 단위 테스트를 실시한다. 자동화 검사 결과와 Android 실기기 결과를 구분하여 기록한다.

- [ ] 광고 실패가 핵심 기능에 영향 없음
- [ ] 광고 위치가 저장·복사·삭제 및 터치 동선과 충돌하지 않음
- [ ] 광고 정책·등록/정산 조건 확인
- [ ] SDK 설정·타입 검사·프로덕션 빌드 통과
- [ ] Android 토스 앱 테스트 번들 검증
- [ ] 비게임 출시 체크리스트 검토
- [ ] **iOS 실기기 검증 미실시 및 남은 위험 명시**

### 11.3 선택 기능·산출물

카메라·OCR은 MVP 필수 합격 조건이 아니다. 구현한 경우에만 별도 검증 결과를 기록한다. 최종 산출물은 앱 소스 코드, 테스트용 빌드, 테스트 결과, 미구현·미검증 항목 목록이다. **개발 완료와 앱인토스 심사 승인·실제 공개는 구분한다.**
